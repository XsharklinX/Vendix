# v3.2 - Cloud opcional

## Objetivo

Permitir acceso remoto solo cuando el negocio realmente lo necesite, sin romper el modo desktop/offline que ya funciona.

## Implementado

### Backend desplegable con PostgreSQL

- `backend/prisma/schema.production.prisma` ahora esta sincronizado con el schema real de la app y usa `postgresql`.
- Scripts nuevos:
  - `npm run cloud:generate`
  - `npm run cloud:push`
  - `npm run cloud:build`
  - `cd backend && npm run db:generate:postgres`
  - `cd backend && npm run db:push:postgres`

### Docker cloud

- `backend/Dockerfile` para construir el backend en Node 20.
- `docker-compose.cloud.yml` con:
  - PostgreSQL 16
  - backend Vendix
  - variables cloud basicas
  - healthcheck de Postgres

### Configuracion cloud

- `backend/.env.cloud.example` documenta variables necesarias:
  - `DATABASE_URL`
  - `JWT_SECRET`
  - `CORS_ORIGIN`
  - flags cloud/sync/backups
  - email SMTP/Resend opcional

### Usuarios por negocio con permisos mas finos

- `User` ahora soporta:
  - `permissions`
  - `disabledAt`
  - `lastLoginAt`
- Login bloquea usuarios desactivados.
- Login actualiza `lastLoginAt`.
- Staff puede guardar permisos JSON.
- `OWNER` y `ADMIN` conservan acceso total.
- `CASHIER` puede recibir permisos como `pos:write`, `sales:read`, `inventory:read`.

### Panel admin/soporte por API

Endpoints reservados a roles `ADMIN` o `SUPPORT`:

- `GET /api/support/overview`
- `GET /api/support/businesses`
- `GET /api/support/businesses/:businessId/health`

Son endpoints de solo lectura para diagnostico: conteos, negocios, salud operativa, deuda pendiente, stock bajo y ultima venta/backup.

### Preparacion para sincronizacion local/cloud

Endpoints nuevos:

- `GET /api/cloud/status`
- `GET /api/cloud/businesses/:businessId/sync-manifest`
- `POST /api/cloud/businesses/:businessId/sync/devices`
- `POST /api/cloud/businesses/:businessId/sync/push`
- `GET /api/cloud/businesses/:businessId/sync/changes`
- `GET /api/cloud/businesses/:businessId/sync/outbox-status`

El manifiesto devuelve conteos y ultimas fechas por entidad para comparar estado local/cloud sin escribir datos.

### Sincronizacion real inicial

Se agregaron modelos persistentes:

- `SyncDevice`: identifica cada desktop, laptop o backend cloud conectado a un negocio.
- `SyncChange`: guarda cambios aplicados por entidad, dispositivo origen, payload, operacion y fecha.

Entidades soportadas en esta primera version:

- `product`
- `client`
- `supplier`
- `employee`

Operaciones soportadas:

- `UPSERT`: crea o actualiza la entidad.
- `DELETE`: marca `deletedAt` cuando la entidad lo soporta.

Politica de conflicto:

- `LAST_WRITE_WINS` para entidades editables.
- `APPEND_ONLY` queda reservado para ventas, caja, pagos y movimientos donde no se debe sobrescribir historia.

Flujo basico:

```http
POST /api/cloud/businesses/:businessId/sync/devices
```

Registra el dispositivo local:

```json
{
  "deviceKey": "desktop-main-uuid",
  "name": "Caja principal",
  "platform": "windows"
}
```

Sube cambios locales:

```http
POST /api/cloud/businesses/:businessId/sync/push
```

```json
{
  "deviceId": "syncDeviceId",
  "changes": [
    {
      "entity": "product",
      "entityId": "product-id",
      "operation": "UPSERT",
      "payload": {
        "name": "Cafe premium",
        "price": 250,
        "cost": 150,
        "quantity": 12
      }
    }
  ]
}
```

Baja cambios de otros dispositivos:

```http
GET /api/cloud/businesses/:businessId/sync/changes?deviceId=syncDeviceId&since=2026-07-04T00:00:00.000Z
```

La respuesta incluye `nextCursor` para guardar el ultimo punto sincronizado.

### Outbox automatico local inicial

Los CRUD principales ahora registran cambios automaticamente en `SyncChange`:

- Productos: crear, editar, eliminar y restaurar.
- Clientes: crear, editar, eliminar y restaurar.
- Proveedores: crear, editar, eliminar y restaurar.
- Empleados: crear, editar, eliminar y restaurar.

Cada cambio queda guardado como `UPSERT` o `DELETE` con politica `LAST_WRITE_WINS`. El registro es tolerante a fallos: si el outbox falla, la operacion principal del usuario no se rompe y se deja un warning en logs.

Estado operativo del outbox:

```http
GET /api/cloud/businesses/:businessId/sync/outbox-status
```

Devuelve total de cambios, ultimo cambio, conteos por entidad, conteos por operacion, ultimos cambios y dispositivos registrados.

### Worker automatico local/cloud

El backend puede ejecutar un worker periodico de sincronizacion. Esta apagado por defecto para no afectar instalaciones offline.

Variables principales:

```env
VENDIX_SYNC_ENABLED=true
VENDIX_CLOUD_URL=https://your-cloud-api.example.com
VENDIX_CLOUD_TOKEN=jwt-del-usuario-en-cloud
VENDIX_SYNC_LOCAL_BUSINESS_ID=negocio-local
VENDIX_SYNC_CLOUD_BUSINESS_ID=negocio-cloud
VENDIX_SYNC_DEVICE_KEY=desktop-main
VENDIX_SYNC_DEVICE_NAME=Caja principal
VENDIX_SYNC_INTERVAL_MS=60000
```

Tambien se puede usar `VENDIX_SYNC_BUSINESS_ID` si el negocio local y cloud comparten el mismo ID.

Que hace el worker:

- Registra el dispositivo local en el backend cloud.
- Lee cambios locales con estado `PENDING` o `FAILED`.
- Envia esos cambios a `/sync/push`.
- Marca cambios enviados como `SYNCED`.
- Marca errores como `FAILED` sin romper la app.
- Baja cambios remotos desde `/sync/changes`.
- Aplica cambios remotos localmente.
- Guarda cambios recibidos como `PULLED`.
- Persiste el cursor en `sync-worker-state.json` dentro de `APP_USER_DATA_PATH`.

Endpoints locales de diagnostico:

```http
GET /api/system/sync-worker
POST /api/system/sync-worker/run
POST /api/system/sync-worker/reload
```

`GET` muestra configuracion efectiva, ultimo error, ultimo push/pull, dispositivo y cursor. `run` fuerza una corrida manual. `reload` reinicia el worker en caliente despues de cambiar configuracion.

### UI segura de Cloud sync

La app instalada ahora permite configurar sync desde `Configuraciones -> Cloud sync`:

- Activar/desactivar worker.
- Guardar URL cloud.
- Guardar token cloud sin volver a mostrarlo en pantalla.
- Definir negocio local, negocio cloud, clave y nombre del dispositivo.
- Elegir intervalo de sincronizacion.
- Ver estado del worker, ultimo envio, ultima recepcion y ultimo error.
- Ejecutar prueba manual con `Probar ahora`.

La configuracion queda en `config.json` dentro de la carpeta de datos de usuario de Electron. Al guardar, la app aplica variables de entorno en runtime y recarga el worker sin exigir reinicio.

## No implementado a proposito todavia

- Multi-dispositivo con sesiones concurrentes avanzadas.
- Backups cloud automaticos a S3/R2/Supabase Storage.
- UI visual del panel admin.
- Captura automatica de operaciones avanzadas fuera de CRUD maestro: ventas, caja, pagos, nomina, movimientos, auditoria y cotizaciones.
- Sincronizacion append-only de ventas, caja, pagos, movimientos y auditoria.
- Resolucion avanzada de conflictos por campo.

Estas piezas requieren decision de arquitectura: si desktop sigue siendo fuente de verdad offline, cloud debe usar colas, versionado por entidad y resolucion de conflictos.

## Flujo recomendado para probar cloud local

```bash
docker compose -f docker-compose.cloud.yml up --build
```

Luego validar:

```bash
curl http://localhost:3100/api/health
```

## Riesgos

- `schema.production.prisma` usa `db push` para arranque rapido; antes de produccion pagada conviene convertirlo a migraciones PostgreSQL versionadas.
- Los permisos granulares estan preparados en backend, pero no todas las rutas aplican `requirePermission` todavia.
- `SUPPORT/ADMIN` deben crearse manualmente por ahora.
- La sincronizacion inicial soporta entidades editables maestras. Ventas/caja deben entrar como append-only para no duplicar o modificar cierres.
- El worker ya puede enviar y recibir cambios, y puede configurarse desde la UI de escritorio. En navegador web sin Electron, la UI muestra estado pero no puede guardar secretos locales.
- `LAST_WRITE_WINS` puede pisar cambios si dos dispositivos editan el mismo registro antes de sincronizar. Para produccion real conviene agregar version por entidad o comparacion por `updatedAt`.
